- **Root cause.** `profile-avatar-upload.ts` passed a `Blob` from `fetch(file://).blob()` to `uploadToSignedUrl`. storage-js 2.105.4 wraps any Blob in `FormData` and ignores `contentType`; Expo fetch (global in SDK 57) writes a part content-type only from `blob.type`, which is empty for a local file, so Storage defaults the part to text/plain and the bucket (`allowed_mime_types` jpeg/png/webp) refuses it.
- **Fix.** Read `response.arrayBuffer()` and upload the raw bytes; storage-js then sends them as the body with `content-type` = the image MIME. Size check uses `byteLength`. Expo's own `blob()` is built from `arrayBuffer()`, so the read path is the one that already worked on device.
- **Test.** New pillar P289 (`apps/mobile/lib/__tests__/profile-avatar-upload-pillar-test.ts`) runs the real supabase-js/storage-js with a capturing fetch and asserts a raw PUT with `content-type: image/jpeg`; observed red (FormData) before the fix. The old avatar tests mocked `uploadToSignedUrl` (hid the bug) and are uncollected; updated to ArrayBuffer anyway.
- **Backend reviewed, unchanged.** PATCH path downloads the object, checks size and magic bytes, writes `profiles.avatar_url` on the service client. Production buckets: private, 5 MB, jpeg/png/webp.
- **Verification run.** type-check, lint:comments, lint:structure, pillar-registry (index regenerated), check-test-collection green; `pnpm test:mobile` 225 / 2178 green. No device run.
- **Follow-up (Tu approved, same session): every Storage upload fixed.** Expo's iOS native fetch builds a `file://` response with `headers: []` (`expo/ios/Fetch/NativeResponse.swift`, non-HTTP `URLResponse`), so every Blob rebuilt from it had no type.
